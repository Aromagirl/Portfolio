# План миграции портфолио Natalia Isakova

## Цель и рамки

Перенести существующее портфолио с `https://sites.google.com/view/natalia-isakova` на **Astro + MDX + GitHub Pages**, максимально сохранив тексты, изображения, встроенные материалы, ссылки, структуру и порядок секций. Переосмысление позиционирования и редактура кейсов выполняются **после** успешного переноса. Старый сайт не изменять и не отключать до проверки нового.

**Основные страницы, подтверждённые при предварительном просмотре:**
- Главная: https://sites.google.com/view/natalia-isakova
- KidswearCycle: https://sites.google.com/view/natalia-isakova/user-research/kidswearcycle
- MyHospital: https://sites.google.com/view/natalia-isakova/user-research/myhospital
- Tickeron: https://sites.google.com/view/natalia-isakova/uxui-design/tickeron

Сначала провести обход навигации и внутренних ссылок, чтобы выявить и другие страницы; этот список не следует считать исчерпывающим.

## Правила миграции

1. Не переписывать, не сокращать и не переводить существующие тексты на этапе извлечения. Оригинальный язык кейсов сохранить.
2. Не заменять реальные скриншоты сгенерированными иллюстрациями или похожими изображениями из интернета.
3. Не терять подписи, порядок медиа, ссылки на прототипы, встроенные видео и цитаты участников исследований.
4. Если файл недоступен автоматически, регистрировать пропуск в отчёте и оставлять на странице понятную временную отметку, не выдумывая содержимое.
5. Не выдавать симуляции персон ИИ за интервью с реальными пользователями. На этапе последующей редакции явно маркировать метод исследования.
6. Оригиналы контента и изображений сохранять отдельно от оптимизированных версий. Не коммитить в публичный репозиторий конфиденциальные документы, приватные материалы, токены, личные сведения третьих лиц.
7. Разделить «миграцию без потерь» и «редакционный редизайн» на отдельные изменения/коммиты.

## Этап 0. Инвентаризация

**Задачи:**
- Собрать карту сайта через меню, все внутренние ссылки и доступные страницы.
- Для каждой страницы посчитать заголовки, текстовые блоки, изображения, видео, встраивания, внешние ссылки.
- Сформировать `migration/manifest.json` с URL-источником, slug, заголовком, типом страницы, списком ресурсов, статусом доступа.
- Проверить Google Sites и Google Takeout как возможные дополнительные источники оригинальных файлов. Экспорт не считать готовым конвертером в Astro. При необходимости попросить исходные файлы Figma, видео или архив экспорта.

**Критерий готовности:** полный список найденных страниц и медиа с отметкой, что доступно и что требует ручного получения.

## Этап 1. Резервная копия

**Задачи:**
- Создать `migration/raw/` и сохранить HTML/текст доступных страниц для внутренней сверки.
- Скачать доступные оригинальные изображения в `migration/assets-original/`, сохранить исходные URL и наименования.
- Выделить встроенные ролики, презентации, внешние документы и прототипы; фиксировать оригинальные URL.
- Для каждого ресурса сохранять источник и связь со страницей и позицией в документе; для доступных файлов вычислять контрольные суммы SHA-256 для поиска дублей.
- Изображения, которые доступны только через браузер или Google Sites, проверять вручную. Не считать ссылку на миниатюру эквивалентом исходника высокого качества.

**Критерий готовности:** резервная копия с воспроизводимым манифестом и перечнем нескачанных ресурсов.

## Этап 2. Новый проект Astro

**Стек:** Astro (статическая генерация), `@astrojs/mdx`, Content Collections с `glob()` loader, TypeScript, CSS (без тяжёлой библиотеки компонентов на старте). GitHub Pages через GitHub Actions.

**Структура:**

```text
portfolio/
├── .github/workflows/deploy.yml
├── astro.config.mjs
├── src/
│   ├── content.config.ts
│   ├── content/projects/
│   │   ├── tickeron.mdx
│   │   ├── myhospital.mdx
│   │   └── kidswearcycle.mdx
│   ├── components/
│   │   ├── ProjectCard.astro
│   │   ├── ImageFigure.astro
│   │   ├── ProjectGallery.astro
│   │   └── Embed.astro
│   ├── layouts/BaseLayout.astro
│   ├── layouts/CaseStudyLayout.astro
│   └── pages/
│       ├── index.astro
│       ├── about.astro
│       ├── contact.astro
│       └── work/[id].astro
├── public/images/projects/{tickeron,myhospital,kidswearcycle}/
├── migration/
│   ├── manifest.json
│   ├── migration-report.md
│   └── scripts/
└── README.md
```

`migration/raw` и исходные приватные/тяжёлые медиа по умолчанию хранить **за пределами публичного репозитория** или исключать через `.gitignore`. Для деплоя нужны только разрешённые публичные изображения.

**Схема данных кейса (frontmatter):**

```yaml
---
title: "Tickeron"
summary: "..."
category: "Product design"
cover: "/images/projects/tickeron/cover.webp"
sourceUrl: "https://sites.google.com/view/natalia-isakova/uxui-design/tickeron"
status: "published" # published | archived | draft
featured: true
sortOrder: 1
roles: []
year: null
---
```

Не заполнять неизвестные факты предположениями. `status` управляет видимостью на сайте, а не сохранностью MDX-файла.

## Этап 3. Автоматическая конвертация

**Задачи:**
- Преобразовать извлечённые HTML-блоки в MDX с сохранением последовательности.
- Корректно обрабатывать заголовки, параграфы, списки, ссылки, цитаты, медиа и подписи.
- Создать компоненты для галерей и встраиваний, не вплетая визуальный стиль в контент.
- Скопировать ресурсы в `public/images/projects/<slug>/`, переименовывать системно (например, `01-overview.webp`). Создать таблицу соответствий исходный URL → локальный путь.
- Сохранить непереносимые HTML-вставки в отдельном реестре и добавить заметные TODO в MDX.
- Для каждой страницы сформировать автоматический отчёт: количество текстовых блоков до/после, количество медиа до/после, найденные битые ссылки.

**Критерий готовности:** все доступные тексты перенесены без смысловой редакции, медиа и ссылки сопоставлены, исключения задокументированы.

## Этап 4. Минимальный дизайн

Сделать **не финальный редизайн**, а качественную нейтральную оболочку:
- Главная: краткое позиционирование, 2–4 избранных проекта, ссылка на все работы, контакт.
- Страница кейса: название, описание, роль (если известна), обложка, содержание MDX, предыдущий/следующий проект.
- About, Contact, адаптивная навигация, простой подвал.
- Responsive на смартфоне, планшете, десктопе; доступность клавиатурой, читаемая типографика, `alt` изображениям.
- Стили и компоненты общие, чтобы обновления дизайна автоматически применялись ко всем кейсам.

На этом этапе не перестраивать старые исследования и не создавать новые кейсы.

## Этап 5. QA и проверка полноты

Для каждой страницы составить таблицу соответствий старый URL ↔ новый URL.

**Проверки:**
- Нет потерянных текстовых разделов и дублирующихся блоков.
- Нет битых внутренних ссылок, `404` для локальных изображений, неверных относительных путей или сломанных видео.
- Порядок экранов и галерей воспроизведён.
- Большие изображения читаемы, миниатюры не используются вместо оригиналов.
- Сборка `npm run build` проходит без ошибок; локальный предварительный просмотр работает.
- Ручная визуальная сверка каждого кейса со старой страницей на мобильном и десктопе.
- Accessibility и базовая производительность (размеры изображений, lazy-loading, CLS) проверены.
- Файлы оригиналов не попали случайно в репозиторий с публичным доступом.

Отчёт `migration/migration-report.md`: статусы `complete`, `needs-manual-asset`, `broken-embed`, `review-needed`; все открытые проблемы перечислены явно.

## Этап 6. GitHub Pages

1. Создать репозиторий. Для бесплатного GitHub Pages использовать публичный репозиторий; исходные материалы проверить на конфиденциальность.
2. В `astro.config.mjs` задать `site` и, при публикации в подкаталог репозитория, `base`. Для репозитория вида `<username>.github.io` или собственного домена настройки отличаются.
3. Добавить workflow `.github/workflows/deploy.yml` на основе официального Astro `withastro/action`, с деплоем через `actions/deploy-pages`.
4. В `Settings → Pages` выбрать GitHub Actions как источник.
5. Проверить опубликованные URL, CSS, изображения, ссылки и метаданные.
6. Добавить sitemap, описания страниц, Open Graph и favicon.
7. При подключении собственного домена настроить DNS, `CNAME`, HTTPS; повторно проверить внутренние пути после удаления/изменения `base`.

**Критерий готовности:** коммит в `main` успешно запускает сборку и обновляет работающий сайт.

## Этап 7. Редактирование без повторной миграции

- Обновить позиционирование на главной (Product Design + создание работающих продуктов с помощью ИИ).
- Переработать Tickeron как приоритетный коммерческий кейс, уточняя собственный вклад и результаты без выдуманных метрик.
- Сократить MyHospital при необходимости, сохранив исследования и изменения после тестов.
- KidswearCycle сохранить в коллекции; можно установить `featured: false` или `status: archived` без удаления материалов.
- SafeClick, Mafia Bot и другие проекты добавлять как отдельные MDX, только с подтверждёнными фактами, правом на публикацию и реальным статусом реализации.
- Рассмотреть второй язык сайта отдельным этапом, не смешивать с миграцией.

## Очерёдность выполнения в Codex

Рекомендуются небольшие отдельные задачи/PR:

1. `chore: inventory Google Sites pages and assets`
2. `chore: backup extracted content and record gaps`
3. `feat: scaffold Astro, MDX and content collections`
4. `feat: import existing portfolio cases`
5. `feat: create reusable portfolio layouts`
6. `test: validate migrated pages against source`
7. `ci: deploy Astro to GitHub Pages`
8. `content: update homepage positioning` (только после успешной миграции)

## Критерии приёмки всего проекта

- [ ] Все публично доступные страницы старого портфолио инвентаризированы.
- [ ] Тексты трёх существующих кейсов перенесены в отдельные редактируемые MDX.
- [ ] Изображения и встроенные материалы восстановлены или отмечены для ручного переноса.
- [ ] Старый сайт остался доступен и неизменён.
- [ ] Новый сайт работает на телефоне и компьютере.
- [ ] Кейсы можно скрывать с главной, не удаляя их.
- [ ] Публикация выполняется автоматически из GitHub.
- [ ] Документация объясняет, как редактировать кейс и добавить новый проект.
- [ ] Отчёт о миграции содержит перечень несоответствий, если они остались.
