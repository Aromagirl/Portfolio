# План перехода раздела Work на каталог проектов с тегами

## Цель

Превратить `/work/` из галереи карточек в каталог проектов с боковой панелью тегов. Сохранить существующий стиль Astro-сайта, URL, обложки и доступный контент. Система должна легко пополняться: для добавления или редактирования проекта достаточно изменить Markdown-файл, не трогая код фильтрации.

## Основное решение

**Источник данных — отдельные Markdown-файлы проектов с YAML frontmatter.** Astro читает их через Content Collections (если в текущем проекте уже есть другой подход к контенту, сначала оценить возможность его расширения, а не создавать вторую систему).

- Один файл соответствует одному проекту; описание и кейс постепенно дополняются внутри него.
- Поля `expertise` и `industries` редактируются вручную и питают фильтры автоматически.
- Список допустимых тегов хранится централизованно, чтобы исключить ошибки написания и дубли вроде `UX/UI` / `UI Design`.
- Карточка может существовать, даже когда кейс ещё не написан.
- Связь с компанией задаётся необязательным `companyId`; компанию не нужно автоматически считать отдельным проектом.

## Предлагаемая модель файлов

Структура примерная, подстроить под имеющийся репозиторий:

```text
src/
  content/
    projects/
      safeclick.md
      fraudscore.md
      mafia-bot-mini-app.md
      tickeron.md
      myhospital.md
      kidswearcycle.md
      ijet-media.md
    companies/                 # необязательно на первом этапе
      ...
  content.config.ts            # схема и валидация полей, если используется Astro Content Collections
  data/
    work-tags.ts               # словарь разрешённых тегов и их названий
  components/
    WorkFilters.astro
    ProjectCard.astro
```

### Шаблон проекта (YAML frontmatter + Markdown)

Сохранить как внутренний шаблон, например `templates/project.template.md`, и копировать при создании нового проекта:

```md
---
title: "Название проекта"
slug: "project-slug"
summary: "Одно-два предложения для карточки"
cover: "/images/projects/project-slug/cover.webp"
companyId: null                  # например: "fraudscore"; необязательно
role: ""                         # заполняется по мере готовности
expertise: []                    # например: ["product-design", "ux-research"]
industries: []                   # например: ["fintech"]
featured: false
order: 100
status: "placeholder"          # placeholder | in-progress | published
visibility: "public"            # public | hidden
---

# Обзор

Кратко: что это за продукт и какую задачу он решает.

## Мой вклад

<!-- Заполнить, когда появится подтверждённая информация. -->

## Процесс и решения

<!-- Исследования, гипотезы, дизайн, разработка. -->

## Результат

<!-- Реальные результаты, если они известны. -->
```

**Важно:** `status` описывает полноту кейса, а `visibility` — видимость проекта в каталоге. Это разные вещи. Пустой кейс с `status: placeholder` и `visibility: public` **виден** как карточка, но не ведёт на фиктивную «готовую» статью.

### Как работают незаполненные проекты

1. Карточка выводится, если `visibility: public`, даже если текст кейса отсутствует.
2. На карточке используются `title`, `summary`, `cover`, необязательная компания и присвоенные теги.
3. Не выводить `Case study coming soon` вместо описания. Если достоверного `summary` нет, показать только название или имеющееся нейтральное описание, не сочинять факты.
4. Если `status: published`, открыть страницу полного кейса. Для `placeholder` и `in-progress` выбрать последовательное поведение: либо компактная страница-обзор с реально имеющимися данными, либо карточка без перехода. **При миграции сохранить существующие ссылки и не создавать 404.**
5. При заполнении Markdown и изменении `status` на `published` тот же проект получает полный кейс без нового ID и без перестройки каталога.
6. `expertise: []` и `industries: []` допустимы: проект показывается в `All`, но не появляется по фильтрам с отсутствующими тегами.

## Теги и автоматизация

Первоначальный утверждаемый словарь:

**Expertise:**
- `product-design` → Product Design
- `ux-research` → UX Research
- `ui-design` → UI Design
- `development` → Development
- `visual-design` → Visual Design
- `marketing` → Marketing

**Industries:**
- `fintech` → Fintech
- `cybersecurity` → Cybersecurity
- `healthcare` → Healthcare
- `ecommerce` → E-commerce
- `gaming` → Gaming

Принципы:

- В Markdown хранить стабильные машинные ключи, а на экране выводить человекочитаемые названия.
- При сборке проверять теги на соответствие словарю (ошибка сборки или ясное предупреждение о неизвестном теге).
- Список чипов и количество проектов по фильтрам выводить из данных, а не прописывать вручную в компонентах.
- Можно показывать только теги, реально используемые хотя бы одним видимым проектом; в перспективе поддержать порядок тегов из словаря.
- **На первом этапе не использовать AI для автоматического назначения тегов.** Теги отражают реальный вклад, поэтому ручной выбор надёжнее. Позднее можно добавить отдельную команду, которая *предлагает* теги по тексту кейса, но не применяет их без подтверждения.
- Если нужен более удобный ввод, оформить для Codex команду: «создай новый проект по шаблону, задай вопросы о роли и навыках и предложи теги из словаря».

## Интерфейс Work

**Desktop:** слева боковая панель шириной около 240–280 px с двумя секциями `Expertise` и `Industries`, справа сетка карточек. Сохранить дизайн-систему сайта, светлую/тёмную темы.

**Фильтрация:** множественный выбор; внутри каждой группы OR, между группами AND. Без выбранных тегов показывать все публичные проекты. Кнопка Clear filters, счётчик найденных проектов, empty state.

**URL:** по возможности синхронизировать выбор с query parameters, восстановление при перезагрузке и Back/Forward.

**Mobile:** кнопка Filters с числом активных фильтров; раскрываемая доступная панель; карточки в одну колонку. Не делать отдельную логику фильтрации для мобильной версии.

**Доступность и производительность:** клавиатура, фокус, `aria-pressed`/семантически подходящие контролы, prefers-reduced-motion, минимум клиентского JS. Все карточки должны быть доступны в исходном HTML для SEO.

## Поэтапный план реализации для Codex

### Этап 1. Аудит без переписывания
- Найти нынешний источник данных семи карточек и роуты проектов.
- Проверить, как устроены Astro pages/content, изображения, dark mode, текущие категории.
- Выбрать минимально инвазивный способ Markdown + schema; сохранить реальные URL.
- Составить таблицу старый URL → файл проекта → новый URL (должен совпадать или иметь корректный redirect).

**Критерий готовности:** понятно, что переносится и что сохраняется; нет дублирующих источников данных.

### Этап 2. Контентная модель и перенос семи проектов
- Создать/адаптировать коллекцию проектов и валидируемый словарь тегов.
- Перенести SafeClick, FraudScore, Mafia Bot & Mini App, Tickeron, MyHospital, KidswearCycle, I-Jet Media.
- Не выдумывать роли, результаты или теги; спорные поля оставить пустыми/пометить TODO.
- Добавить файл-шаблон нового проекта и краткую инструкцию по заполнению.
- Для компаний на первом этапе достаточно необязательного `companyId`; отдельные страницы компаний не нужны.

**Критерий готовности:** все семь карточек рендерятся из Markdown; пустые проекты не теряются.

### Этап 3. Каталог и фильтры
- Переработать `/work/`: sidebar + grid, убрать прежние горизонтальные фильтры.
- Подключить теги к YAML-полям и динамически вычислять результаты.
- Сделать счётчик, сброс, пустое состояние, фильтры в URL (при разумной сложности).
- Сохранить все действующие ссылки карточек.

**Критерий готовности:** редактирование YAML меняет состав фильтров/результатов без изменения UI-кода.

### Этап 4. Адаптивность и проверка
- Реализовать мобильную панель фильтров и планшетное поведение.
- Проверить keyboard navigation, темы, SEO, сборку Astro и все URL.
- Проверить: нет тегов; один тег; несколько из одной группы; теги из двух групп; нет результатов; пустой кейс; опубликованный кейс.

**Критерий готовности:** фильтрация и маршруты работают на desktop/mobile, сборка успешна.

### Этап 5. Дальнейшее наполнение (без блокировки релиза)
- Постепенно дописать кейсы в тех же `.md` файлах и выставить `status: published`.
- При необходимости добавить схемы и страницы компаний с несколькими проектами.
- Позже рассмотреть AI-предложение тегов по содержанию Markdown с обязательным ручным подтверждением.

## Как я буду добавлять проект

1. Скопировать `templates/project.template.md` в папку проектов.
2. Заполнить `title`, `slug`, `summary`, `cover`; при необходимости `companyId`.
3. Выбрать `expertise` и `industries` из словаря; можно пока оставить пустые массивы.
4. Выставить `status: placeholder` или `in-progress` и `visibility: public`.
5. Позже дополнять текст кейса и в конце менять `status` на `published`.
6. Запустить сборку: неизвестные теги/неверные поля должны быть выявлены валидацией.

## Что не делать сейчас

- Не создавать полноценный каталог компаний и страницы каждой компании.
- Не переделывать главную, About или общую визуальную систему.
- Не переписывать содержимое кейсов и не генерировать неподтверждённые результаты.
- Не делать AI-автотегирование, сложную админку или CMS.
- Не менять текущие URL без явной необходимости.
